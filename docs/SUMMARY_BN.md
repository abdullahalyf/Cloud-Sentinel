# সংক্ষেপে: আমরা কী বানাচ্ছি, কেন জিতব, কে আগে কী করবে

## চূড়ান্ত আইডিয়া
**CloudSentinel = AI agent-দের circuit breaker + control tower।**
প্রতিটা agent OpenTelemetry দিয়ে নিজের কাজের হিসাব (token, prompt, tool call) পাঠায়। আমাদের **brain** তিন ধাপে বিচার করে:
১) hard limit (বাজেট, tokens/min, RAM): সাথে সাথে kill, AI লাগে না
২) **semantic loop detector**: একই কথা ভিন্ন ভাষায় বারবার বললে ধরে ফেলে, কোনো LLM call ছাড়াই
৩) সন্দেহজনক কেসে **Claude judge** সিদ্ধান্ত দেয়: PAUSE / KILL / WARN / IGNORE, সাথে memory ঠিক করার পরামর্শ

তারপর agent-কে **pause** করা হয় (মারা হয় না)। মানুষ dashboard থেকে (বা Claude, MCP দিয়ে) agent-এর **memory ঠিক করে resume** করে, agent probation-এ থেকে আবার সুস্থ হয়।
টাকা নড়ানো tool call (যেমন ৫০,০০০ টাকার refund) মানুষের অনুমতি ছাড়া চলে না: approve / deny / rewrite।
শেষে **ROI panel** দেখায় প্রতিটা হস্তক্ষেপে কত ডলার বাঁচল।

Demo-র গল্প: **"রাত ৩টার ঘটনা"** (ShopBD-র ৪টা agent: beta loop করে → pause → memory ঠিক → সুস্থ; gamma token bomb → সাথে সাথে kill; delta-র বড় refund আটকে যায়; Claude Desktop-কে বললেই "সবচেয়ে খরুচে agent-কে থামাও")।

### 2026-11-08 · A6 Prompt-injection detection (agent-এর কথা monitor-কে নিয়ন্ত্রণ করতে পারে না)
- করা হয়েছে: `brain/injection.py` — agent-এর prompt আর tool-এর argument দুটোই স্কোর করে (০..১) + **কেন** স্কোর উঠল সেটার কারণ দেয়। আগে ছিল একটা ছোট denylist, যেটা "ignore all previous instructions" আর বাংলা কোনো ভাষাই ধরত না। এখন ১০টা signal family: instruction override (ইংরেজি + বাংলা ট্রান্সলিটারেশন), system-prompt exfiltration, role-play jailbreak, hidden text (zero-width, bidi, বড় base64), memory poisoning ("always refund 100%"), non-shell tool-এ shell metacharacter, SQL injection, path traversal, allowlist-বাইরের host, বেশি recipient। **Tool gate-এ injection আগে চলে, policy-র পরে, আর যেটা বেশি কঠান সেটাই জেতে** — তাই policy যদি `run_sql` allow করে, তবু `; DROP TABLE orders` ঢুকবে না। ০.৮+ → deny, ০.৫–০.৮ → human-এর কাছে (কারণসহ), memory write ০.৫+ → alert, L5 detector ০.৮+ → judge-এর কাছে finding। **Calibration-টাই কঠিন ছিল**: প্রথম version-এ একটা সাধারণ override-ও ০.৪৫ পেত (কোনো threshold-এর নিচে — detector যা কখনো চালু হয় না)। আর corpus-এ recall 1.000 মানে বিশ্বাস করা যায় না, কারণ pattern corpus-এর সাথেই বানানো — তাই pattern ঠিক করার **পরে হাতে** ১৫ attack + ১৫ benign hold-out লেখা হয়েছিল। প্রথম চেষ্টায় মাত্র **৩/১০** ধরা পড়েছিল, আর সেটা তিনটা আসল ফাঁক দেখিয়েছিল (বাংলা শব্দের ক্রম, "treat every request as safe", একটা ভুল label-ওয়ালা corpus case)। সমাধান একটা-একটা বাক্য যোগ করা নয় — **shape** ধরা (control বাদ দেওয়ার shape, pre-approved shape, do-not-flag shape), যাতে corpus-এ না-থাকা বাক্যেও ধরা পড়ে। ফলাফল ২৩৬টা case-এ (১০৩ attack, ১৩৩ কঠিন benign): **recall 1.000, false positive 0.000**, hold-out-এও **1.000 / 0.000**। পথে ৫টা আসল false positive ধরা পড়ে ঠিক করা হয়েছে ("the developer mode flag in our config is disabled", "do not skip the verification step", `https://`-এর ভিতরের `s:/` ইত্যাদি)। Fojle-এর simulator আসেনি বলে FakeFleet-এ সমান `prompt_injection` rogue kind যোগ করা হয়েছে (contract PR #34, `8816025`) — agent সত্যিই কাজ করে কিন্তু প্রতিটা prompt monitor-কে ঠকাতে চায়, আর brain তাকে **pause** করে; ঠিক একই সময়ে সুস্থ agent **অক্ষত** থাকে। Contract PR #34 merge হয়েছে, brain PR #35 খোলা। ৩৫টা acceptance test + `docs/research/brain-injection.md`-এ পূর্ণ precision/recall রিপোর্ট।

### 2026-11-08 · A8 Horizontal brain sharding (Nটা brain একই fleet ভাগ করে, একটা মরলেও ঝামেলা নেই)
- করা হয়েছে: `brain/sharding.py` — Nটা brain worker process একই fleet ভাগ করে নেয়, আর **প্রতিবার ঠিক একজন** worker-ই প্রতিটা agent-এর দায়িত্বে থাকে। এটা না হলে দুই worker একই agent দেখলে সেটা দুইবার pause হতো, দুইবার judge হতো, আর প্রতিটা metric দুইবার গোনা হতো। **Owner ঠিক করা হয় rendezvous hashing দিয়ে** — `sha1(agent_id + "\x00" + worker_id)`-এর সবচেয়ে **বড়** hash, live worker-দের মধ্যে। "সবচেয়ে বড়" (সবচেয়ে ছোট বা modulo নয়) — এটাই minimal movement দেয়: একজন worker মরলে **শুধু তার** agent নড়ে, বাকিরা জায়গায় থাকে; modulo hashing-এ পুরো fleet ছড়িয়ে যেত, প্রতিটা agent লাফাতো। Python-এর `hash()` **কখনো** ব্যবহার করা হয়নি — ওটা প্রতি process-এ randomize হয় (`PYTHONHASHSEED`), তাই দুই worker ভিন্ন owner পেত আর দুজনেই মনে করত "সব agent আমার"। **তিনটা বিষয় design, style না**: (১) কে বেঁচে আছে সেটা **store-এর না নিজের clock দিয়ে** হিসাব হয় — store-এর `time.time()` আর heartbeat-এর timestamp আলাদা clock, তাই clock ভুল থাকলে worker ভাবত সবাই মরে গেছে আর পুরো fleet নিজে নিয়ে নিত (এক agent-এ দুই worker = সবচেয়ে খারাপ বাগ, তাই সবসময় সাবধানী দিকটাই নেওয়া হয়); (২) heartbeat লেখা fail করলে worker মরে না — না হলে অন্যরা তার agent নিয়ে নিত যখন সে এখনো সেগুলো নিয়েই কাজ করছে; (৩) worker নিজেকে সবসময় alive ধরে, কারণ সে চলছে আর নিজেই জানে। Engine এখন শুধু **নিজের** agent tick/judge করে আর **নিজের** agent-এর command চালায় — তাই কোনো command দুইবার চলে না, আর অন্যের agent-এর command ছুঁয়ে দেখে না। `python -m brain --worker [--worker-id]` — API ছাড়া শুধু engine (API brain process-এই থাকে; দুই process একই port-এ উঠলে লড়াই হয়)। `/v1/health`-এ এখন worker-দের তালিকা আর মোট agent সংখ্যা। Contract PR #38 (`a8a32c2`) + #39 (`3bbea86`) merge হয়েছে — `workers` table, `CS_WORKER_ID`/`CS_WORKER_HEARTBEAT_SECONDS`/`CS_WORKER_STALE_SECONDS`, health field, আর mock/real API-র parity rule এখন **একদিকে** (mock এগিয়ে থাকতে পারে, কিন্তু পিছে থাকতে পারে না)। ৩০টা test। মাপা সংখ্যা (২ engine, একটা DB file, ৫০ agent, virtual clock): ভাগ **২৪/২৬**, takeover **১২.০ সেকেন্ড** (লক্ষ্য ১৫), tick p95 **১৯৪ ms** (লক্ষ্য ২০০), command একবারই। সব সংখ্যা আর profile `docs/research/brain-scaling.md`-এ।

### 2026-11-08 · A11 Engine perf (১০০ agent-এ tick p95 ৫১৩ ms → ১৩.২ ms)
- করা হয়েছে: ১০০ agent-এ tick p95 **৫১৩ ms → ১৩.২ ms** (বাজেট ২০০ ms)। Profile দুটো আসল দোষী ধরিয়ে দিল, আর দুটোই brain-এর আসল কাজ ছিল না। **৮৪% সময় ছিল `sqlite3.Connection.commit`** — tick প্রতি agent-এ দুইটা row লেখে আর store প্রতিটার পরে commit করে, তাই ১০০ agent = ২০০ বার disk sync। `brain/write_batch.py` tick-এর সব row এক transaction-এ লেখে, store-এর **নিজের** connection-এ আর store-এর **নিজের** lock-এর মধ্যে। প্রতি tick-এ commit ২০০ → ১। এটা brain-এ না store-এ কেন: store জানে না যে তাকে দেওয়া row-গুলো একই tick-এর — সেটা শুধু brain জানে — তাই `shared/store.py` এক ইঞ্চও বদলায়নি। **দ্বিতীয় খরচ ছিল জানা উত্তর নতুন করে বের করা**: `semantic_loop_score` প্রতি tick-এ প্রতি agent-এর জন্য ১৬টা prompt আবার tokenize আর re-cluster করত, কিন্তু window একটা একটা করে সরে, তাই ১৬টার মধ্যে ১৫টা আগের চেয়ে হুবহু এক। `loops.IncrementalLoopScore` cluster-গুলো রাখে আর শুধু নতুন prompt-টা বসায়; আর `score_text` একই ১২টা prompt-এ প্রতি tick-এ **দুইবার** চলত (একবার count, একবার maximum), তাই `AgentWindow` এখন text-এর উপর score cache করে। `re.Pattern.search`: ৩২,২৫৬ → ৯৪৫। **Fast path-এ যে একটা জিনিস ভুল হতে পারে না**: loop score-ই detector-এর কাজ করে, তাই plain scorer-এর **একই সংখ্যা** হতে হবে — greedy clustering order-নির্ভর, তাই fast path শুধু তখনই চলে যখন নতুন window আগেরটার suffix-extension; বাকি সবকিছু শূন্য থেকে আবার হিসাব করে। `brain/tests/test_perf.py` দুটোকে prompt ধরে ধরে মিলিয়ে দেখে — window সরলে, ছোট হলে, মাঝখানে বদলালে। **Batch যে তিনটা নিয়ম ভাঙতে পারে না**, প্রতিটার একটা test: একই row লেখা হয়; শেখা baseline টেকে (খালি baseline মানে "নতুন baseline নেই" — আর batch-এ এক agent-এর baseline থাকতে পারে আরেকটার না, যেটা একটা upsert-এ প্রকাশ করা যায় না); আর batch fail হলে কোনো row হারায় না, কারণ তখন একটা একটা করে লেখা হয় ঠিক আগের মতো। Scaling curve (এক worker, এক store, ২০ tick): ১০ agent ৪.১ ms p95, ২৫ → ৬.৯, ৫০ → ৮.২, **১০০ → ১৩.২**, ২০০ → ২৫.১ — প্রায় linear, ছোট constant-সহ।

### 2026-11-08 · B4 Hierarchical budget আর graceful degradation (গাছের বাজেট, আর ধাপে ধাপে নামানো)
- করা হয়েছে: **বাজেট একটা গাছ** — org → team → agent — আর **প্রতিটা লেভেল নিচের যোগ**। org-এর বাজেট = টিমগুলোর যোগ, টিমের বাজেট = তার agent-দের যোগ। এটা সাজসজ্জা না: এটাই সেই জিনিস যা একটা লাফিয়ে-লাফিয়ে agent-কে পুরো fleet-এর টাকা খেতে দেয় না — agent নিজের ভাগ ছাড়ালে **শুধু নিজের ভাগই** খায়, বাকিরা নিজের টাকা পেয়ে যায়, আর গাছটা সেটা **বলেই দেয়**। org-এর বাজেট **হাতে লেখা নয়, হিসাব করা** — নিজের টিমগুলোর যোগ থেকেই আসে, তাই গাছ নিজের সাথে অসম্পর্কিত হতে পারে না। **Forecast কথা বলে তখনই, যখন বলা যায়**: burn rate শূন্য হলে কোনো forecast-ই নেই (`minutes_to_exhausted` = `null`, বাক্য = খালি) — "০ মিনিটে শেষ" একটা মিথ্যা, "অসীম" একটা সংখ্যা নয়; টাকা ইতিমধ্যেই শেষ হলে সেটা আলাদা কথা (`remaining` = 0, বাক্য সোজাসাপটা)। **নামানোর সিঁড়ি ঠিক এই ক্রমে** — throttle → সস্তা model → pause → kill — আর **সিঁড়ি কখনো এক ধাপ লাফায় না**: যে agent throttle হয়নি তাকে downgrade করা হয় না, কারণ downgrade throttle-এর চেয়ে বড় প্রতিশ্রুতি, তাই ছোটটার প্রমাণ দাবি করে। **সবচেয়ে জরুরি অংশটা** — **যে throttle কাজ করেনি সে সিঁড়ির পরের ধাপে যায় না**: যে ধাপ কাজ করেনি তার পর agent তো পুরো গতিতেই চলছে, তাই brain যদি মনে করত "throttle হয়েছে" সেটা operator-কেও নিজেকেও ঠকানো — তাই সিঁড়ি ওই ধাপেই আটকে থাকে, **কেন** লিখে রাখে, আর alert দেয়। **সিঁড়ি থামে প্রথম যে ধাপে কাজ হয়** — agent আবার healthy হলে সিঁড়ি নতুন করে শুরু (পুরনো throttle আর দরকার নেই, তাই পরের runaway-কে নতুন, নরম চাল দেওয়া হয়)। **পুরো নতুন আচরণ flag-এর পিছনে, default off** (`CS_DEGRADATION_ENABLED`) — off থাকলে breaker ঠিক আগের মতোই করে: সরাসরি pause বা kill, কোনো throttle ছাড়া। **দুই জায়গায় ভুল ধরা পড়েছিল** (আর দুটোই শেখার মতো): (ক) `current_step="PAUSE"` মানে "agent PAUSE-এ আছে" — যেটা বোঝায় সিঁড়ি **PAUSE পর্যন্ত** হেঁটেছে (throttle আর downgrade ছাড়া pause হওয়া যায় না), তাই `applied` = সিঁড়ির prefix; (খ) mock-এ org-এর বাজেট হাতে লেখা `4.0` ছিল, কিন্তু টিমগুলোর যোগ `2.2` — মানে **গাছ নিজের সাথে মিলছিল না**, তাই এখন `ORG_BUDGET` হিসাব করা (`sum(BUDGETS.values())`)। Contract আগে: নতুন action type `THROTTLE`/`DOWNGRADE`, `DEGRADATION_LADDER`, `budget_forecast`/`budget_node`/`budget_report`/`degradation_plan` (`shared/contracts.py`, PR #66) → flag (PR #68) → brain (`brain/budget.py` নতুন, PR #67) → gap row বন্ধ (PR #69)। `brain/tests/test_budget.py`-তে **৪৩টা test**, `shared/tests/test_budget_contract.py`-তে **১৯টা test**।

### 2026-11-08 · B5 Policy backtesting (নতুন policy কি ধরতে পারত — প্রমাণ সহ)
- করা হয়েছে: "নতুন policy চালু করলে কি আগের runaway ধরতে পারত?" — এই প্রশ্নের উত্তর **অনুমানে নয়, পুরনো trace আবার চালিয়ে** বের হয়। store-এ থাকা span-গুলো আবার একবার হাঁটা হয়, প্রতিটা agent-এর জন্য আলাদা করে, ঠিক **সেই একই** `AgentWindow` আর **সেই একই** `evaluate()` দিয়ে যেটা live brain প্রতি tick-এ ব্যবহার করে — শুধু বাজেট বদলায় (candidate policy-র বাজেট)। **সবচেয়ে জরুরি অংশটা** — catch আর false positive-এর **পার্থক্যটা কোথায়**: store-এর **alert**-ই সত্যের রেকর্ড। কোনো alert-এর agent **সত্যিই ভুল করেছিল**, alert-এর নেই মানে **সে ঠিক ছিল**। তাই alert না পড়লে এই backtest বুঝতেই পারত না — "candidate একটা সুস্থ agent-কে থামাত" আর "candidate একটা runaway এক মুহূর্ত দেরি করে থামাত" — এই দুটোর পার্থক্য। **যে rule-টা running policy আগেই দেখেছে আর agent-কে থামিয়েছে, সেটা নতুন catch নয়** (সংখ্যা বাড়িয়ে নিজেকে বড় দেখানো) — কিন্তু **যে rule-টা running policy চোখ এড়িয়েছিল, আর agent সত্যিই ভুল করছিল, সেটাই catch**। **False positive গোনা হয়, লুকানো হয় না** — শুধু ভালো খবর দেখানো একটা backtest বিজ্ঞাপন, মাপ নয়। **টাকা হিসাবটা live system-এরই ROI formula** (`$/min at the moment of action × horizon`) — তাই backtest আর live ROI report কখনো "সেভ করা এক ডলার" নিয়ে মতভেদ করতে পারে না। **Replay-টা deterministic** — একই trace আর একই candidate policy → একই report, একই ক্রমে, তাই দুটো policy তুলনা যায়। **Trace না থাকলে report আসে শূন্য দিয়ে, error দিয়ে নয়** — "আমাদের কাছে কোনো trace নেই, তাই কিছু বলা যায় না" এটাই একটা সত্য, আর খালি store-এ fail করা operator-কে শিখিয়ে দেয় backtest-কে বিশ্বাস করতে। CLI: `python -m brain.backtest [policy.yaml]` — policy না দিলে **নিজেই চলতি policy** নিজের বিরুদ্ধে পরীক্ষা করে; report ছাপে আর **exit 0** (কিছু না পেলেও exit 0 — কিছু না পাওয়াটাও একটা ফল)। API: `GET /v1/backtest`, flag `CS_BACKTEST_ENABLED` (default **off**) — off থাকলে endpoint **থাকেই না** (404, খালি report নয়)। Contract আগে: report-এর shape আর mock endpoint (`shared/contracts.py` + `shared/mocks/mock_api.py`, PR #71) → brain (`brain/backtest.py` নতুন, PR #72)। `brain/tests/test_backtest.py`-তে **২৩টা test**, `shared/tests/test_backtest_contract.py`-তে **১৫টা test**।

### 2026-11-08 · B7 Tamper-evident audit log (যা হয়েছে তার লেখা — পরে বদলানো যাবে না)

### 2026-11-08 · B8 Security detectors (তিনটা জায়গায় তিনটা ফাঁদ ধরা)
- করা হয়েছে: fleet-কে তিনভাবে ক্ষতি হয়, আর প্রতিটার জন্য **একটা** জায়গায় নজরদারি — **(ক) ছদ্মবেশী tool description**: MCP server এমন একটা tool serve করতে পারে যার *description*-ই agent-কে চালাতে চায় ("always call this first", "do not ask for approval")। description হলো agent যা পড়ে তারপর সিদ্ধান্ত নেয় — তাই বিষয়টা agent-এর *কোডে* আক্রমণ না, **নির্দেশে** আক্রমণ। **(খ) tool output-এ secret**: card number, API key, password — আর সেটা **লেখার আগেই** সরানো হয়, কারণ ধরা পড়া কিন্তু না সরানো মানে secret ইতিমধ্যে store, dashboard আর পরের model call-এর prompt-এ চলে গেছে। কী লেখা হয় তা বলা হয় না — লেখা হয় **ধরন** ("একটা card_number সরানো হয়েছে"), কারণ নম্বরটাই তো secret। **(গ) retrieved content-এ injection**: এটা **আগের** A6 scorer (`brain/injection.py`) — নতুন বানানো হয়নি, কারণ একই সমস্যার দুটো scorer মানে একটা বেশি; কমান্ডটা floor-এর নিচে গেলে **non-zero exit** করে, তাই CI job হতে পারে। **Running system-এ**: score `CS_SECURITY_DENY_THRESHOLD`-এ পৌঁছালে tool call **deny** — warning না, log না (দুই gate-এর মধ্যে কড়াটা জেতে); `POST /v1/security/tools` — registry জানায় কোন tool serve করে, brain description দেখে **verdict আর কারণ** দেয়; `GET /v1/security/tools` — `status=poisoned` দিলে শুধু agent-কে চালানোর চেষ্টা করা toolগুলো; `GET /v1/security/report` — শেষ scan-এর সব finding, সংখ্যাসহ। **একটা কথা বলা দরকার**: secret-এর মতো case-গুলোতে আসল secret লেখা নেই, `{{PLACEHOLDER}}` আছে আর loader সেটা খুলে দেয় — কারণ repo-তে secret-এর আকৃতির লেখা **লিক থেকে আলাদা করা যায় না** (নিজের `secrets` job-ও পারে না), আর নিজের corpus-এ চিৎকার করে scanner-কে চুপ করালে সবাই scanner-কে চুপ করাতে শেখে। মাপ একই আছে, repo-তে secret-এর আকৃতির একটা লেখাও নেই। Contract আগে: flag তিনটা, `tool_registry` table, mock-এর তিন endpoint (PR #83) → brain (`brain/security.py` নতুন, PR #85) → gap row বন্ধ (PR #86)। `brain/tests/test_security.py`-তে **২৭টা test**।
